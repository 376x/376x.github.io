用 Lifespan 管理 FastAPI 应用资源

2026-08-22 # FastAPI# Lifespan# 最佳实践

数据库连接池、HTTP 客户端、缓存连接 —— 这些资源要跟着应用一起创建和销毁。 老教程里的 @app.on_event("startup") 已经被官方标记为废弃， 现在的标准答案是 Lifespan。它不仅没变复杂，反而更优雅了。

1. 为什么 on_event 被废弃

旧写法把启动和关闭逻辑拆散在多个装饰器回调里：

# ❌ 旧写法（已废弃）
@app.on_event("startup")
async def startup():
    app.state.pool = await create_pool(...)

@app.on_event("startup")
async def another_startup():
    ...

@app.on_event("shutdown")
async def shutdown():
    await app.state.pool.close()
  • 同一个资源的创建/销毁逻辑分散在两个地方；
  • 多个 startup 回调之间的执行顺序、依赖关系不明确；
  • 无法使用 contextmanager 的异常语义（比如只清理已成功创建的资源）。

2. Lifespan：一个函数管到底

Lifespan 是一个基于 asynccontextmanager 的异步上下文： yield 之前是启动逻辑，之后是关闭逻辑，天然对称：

from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ---- startup ----
    resources = await setup()
    yield                       # ---- 应用运行中 ----
    # ---- shutdown ----
    await teardown(resources)

app = FastAPI(lifespan=lifespan)

如果 startup 阶段抛异常，服务不会带着残缺状态启动； shutdown 阶段则可以按依赖顺序逐层清理 —— 这些语义都是 contextmanager 自带的。

3. 生产可用的完整模板

下面是我在项目里使用的模板：数据库连接池 + 共享 HTTP 客户端， 全部挂在 app.state 上：

from contextlib import asynccontextmanager
from typing import AsyncIterator

import httpx
from fastapi import FastAPI, Request
from sqlalchemy.ext.asyncio import (
    AsyncSession, async_sessionmaker, create_async_engine
)

DATABASE_URL = "mysql+aiomysql://user:pass@localhost/app"

@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    # startup: 创建引擎与连接池
    engine = create_async_engine(DATABASE_URL, pool_size=10, max_overflow=5)
    app.state.session_factory = async_sessionmaker(engine, expire_on_commit=False)

    # startup: 复用一个带连接池的 httpx 客户端
    app.state.http = httpx.AsyncClient(timeout=httpx.Timeout(5.0))

    yield

    # shutdown: 注意关闭顺序，后建的资源先关
    await app.state.http.aclose()
    await engine.dispose()

app = FastAPI(lifespan=lifespan)

两点工程细节：

  • httpx.AsyncClient 必须复用。每个请求新建客户端意味着每次都要经历 DNS/TCP/TLS 握手，连接池白瞎了；
  • 关闭顺序与创建顺序相反：http.aclose() 在前，engine.dispose() 在后。

4. 与依赖注入配合使用

app.state 只是全局容器，真正把它接入类型安全的体系靠依赖。 路由里通过依赖拿到 session 工厂，测试时也能整体替换：

from typing import Annotated
from fastapi import Depends

def get_session_factory(request: Request) -> async_sessionmaker[AsyncSession]:
    return request.app.state.session_factory

SessionFactory = Annotated[
    async_sessionmaker[AsyncSession],
    Depends(get_session_factory),
]

@app.get("/users/{uid}")
async def get_user(uid: int, factory: SessionFactory):
    async with factory() as session:
        user = await session.get(User, uid)
        return {"id": user.id, "name": user.name}

这样资源生命周期由 lifespan 统一管理，获取路径由依赖统一声明 —— 路由代码不出现任何"从哪拿资源"的细节。

5. 多个子应用/一长串资源的组织技巧

资源多了以后 lifespan 会变得很长，可以用嵌套的 asynccontextmanager 组合：

@asynccontextmanager
async def with_db(app: FastAPI):
    app.state.engine = create_async_engine(DATABASE_URL)
    yield
    await app.state.engine.dispose()

@asynccontextmanager
async def with_http(app: FastAPI):
    app.state.http = httpx.AsyncClient()
    yield
    await app.state.http.aclose()

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with with_db(app), with_http(app):   # 支持多层嵌套
        yield

app = FastAPI(lifespan=lifespan)

每个 resource 一个函数、独立可测，最后组合成总 lifespan —— 清晰且不失优雅。

小结

  • on_event 已废弃，新项目一律用 lifespan 参数；
  • Lifespan = 一个 asynccontextmanager，yield 前启动、后清理；
  • 资源挂 app.state，通过 Request 依赖暴露给路由，保持类型安全；
  • 资源多了就拆成多个小 contextmanager 嵌套组合。
