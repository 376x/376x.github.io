FastAPI 异步避坑指南：async def 还是 def？

2026-08-18 # FastAPI# Asyncio# 性能

FastAPI 最吸引人的卖点之一是"原生异步"，但线上事故里最常见的性能问题恰恰也是异步用错了。 典型症状：平时接口很快，某个接口一慢，整个服务所有接口一起卡死。 这篇文章把这个问题的根因和应对方案一次性讲清楚。

1. 先搞清楚你的代码跑在哪里

FastAPI 对两种路由函数签名的处理方式完全不同：

声明方式运行位置并发能力来源
async def主事件循环（单线程）await 让出控制权时的任务切换
def外部线程池（默认约 40 线程）多线程并行处理同步阻塞调用

关键点：事件循环是单线程的。 所有 async def 路由共用这一个线程，任何一个协程不释放控制权， 其他所有请求就都得排队。

2. 反面教材：一个拖垮全站的接口

# ❌ 千万不要这样写
import time
import requests

@app.get("/products/{pid}")
async def get_product(pid: int):
    resp = requests.get(f"https://erp.internal/api/products/{pid}")  # 同步 IO！
    time.sleep(0.5)                                                   # 更致命！
    return resp.json()

requests.get 和 time.sleep 都是同步阻塞调用： 在 async def 里执行时不会让出事件循环， 期间到达的所有请求全部堆积。压测表现通常是：这个接口 QPS 很低的同时， 其它本来正常的接口延迟也跟着暴涨。

3. 正确姿势一：全程异步

IO 栈有异步实现时，这是最优解：

import asyncio
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI, Request

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with httpx.AsyncClient(timeout=5) as client:
        app.state.http = client
        yield

app = FastAPI(lifespan=lifespan)

@app.get("/products/{pid}")
async def get_product(pid: int, request: Request):
    client: httpx.AsyncClient = request.app.state.http
    resp = await client.get(f"https://erp.internal/api/products/{pid}")
    await asyncio.sleep(0.5)   # 异步等待，期间其他请求正常运行
    return resp.json()

判断标准很简单：每个 await 点都必须是真的异步。 数据库用 asyncpg / SQLAlchemy async，Redis 用 redis.asyncio，HTTP 用 httpx / aiohttp。

4. 正确姿势二：丢进线程池

当调用的库只有同步实现（很多老牌 SDK 就是这样），把它丢进线程池执行：

from fastapi.concurrency import run_in_threadpool

def sync_query_erp(pid: int) -> dict:
    conn = pymssql.connect(...)          # 只有同步驱动的内部系统
    return query_product(conn, pid)

@app.get("/legacy-products/{pid}")
async def get_legacy_product(pid: int):
    data = await run_in_threadpool(sync_query_erp, pid)
    return data

或者最省事的方式 —— 把路由直接写成普通 def， FastAPI 会自动放到同一个线程池：

@app.get("/legacy-products/{pid}")
def get_legacy_product(pid: int):     # 普通 def，自动走线程池
    return sync_query_erp(pid)

5. 决策表

场景推荐写法
IO 且有异步库（DB/HTTP/Redis）async def + await 异步调用
IO 但只有同步库def 路由，或 run_in_threadpool
CPU 密集（图像处理、加解密、大计算）进程池（ProcessPoolExecutor）或独立 worker 服务
混合同步+异步异步入库，同步片段包 run_in_threadpool

CPU 密集任务要特别注意：即使是 def 路由（线程池），Python GIL 也会让纯计算互相争抢， 大计算量应使用进程池：

import asyncio
from concurrent.futures import ProcessPoolExecutor
from functools import partial

process_pool = ProcessPoolExecutor(max_workers=4)

def heavy_hash(data: bytes) -> str:
    import hashlib
    return hashlib.pbkdf2_hmac("sha256", data, b"salt", 200_000).hex()

@app.post("/hash")
async def make_hash(payload: DataIn):
    loop = asyncio.get_running_loop()
    digest = await loop.run_in_executor(process_pool, heavy_hash, payload.data)
    return {"digest": digest}

6. 怎么发现有人在阻塞事件循环？

  • 开发环境开启 asyncio 慢回调日志：loop.slow_callback_duration 配合 -X dev；
  • 使用 BlockBuster 这类库，在测试中对阻塞调用直接抛异常；
  • 上线前用 locust 压测：观察单接口变慢时其它接口的 P99 是否连带恶化 —— 连带恶化基本就是事件循环被堵了。

小结

  • async def 里不允许出现任何同步阻塞调用 —— 这是铁律；
  • 没把握就用 def，FastAPI 的线程池兜底非常可靠；
  • CPU 密集交给进程池或独立服务，别让 Web 进程算数；
  • 监控上盯住"多接口 P99 同时恶化"这一特征信号。
